# 设计说明

## 1. 整体结构

```
┌─────────────────────────── GUI（PySide6 主线程）───────────────────────────┐
│  主窗口：流列表 / 详情地址 / 日志       流配置对话框：视频源 + 厂商路径    │
└───────────────────────────────┬───────────────────────────────────────────┘
                                │ Engine（engine.py）
        ┌───────────────────────┴────────────────────────┐
        │                                                │
┌───────▼────────────────────┐              ┌────────────▼─────────────────┐
│ RtspServer（rtsp/server.py）│              │ StreamSource（media/source） │
│  · 监听 8554，一连接一线程  │◄──路由表────►│  · 一个 ffmpeg 子进程        │
│  · 会话 / 通道 / UDP·TCP    │              │  · TS 解复用 → 帧 + PTS      │
│  · RTCP SR 定时器           │◄──RTP 分发───│  · 按真实时间匀速推送        │
└────────────────────────────┘              └────────────┬─────────────────┘
                                                         │ stdout（MPEG-TS）
                                              ┌──────────▼──────────┐
                                              │  ffmpeg 转码进程     │
                                              │  任意格式 → H.264/H.265│
                                              └─────────────────────┘
```

一个 `StreamSpec`（一路虚拟摄像机）= 一个 `StreamSource`（编码进程）+ N 条 `Route`（厂商路径）。
N 个客户端连到任意一条 Route，都从同一个 `StreamSource` 取同一份帧，只是各自持有独立的
RTP 序号（seq）、SSRC 和时间戳基准，互不影响。

## 2. 媒体链路

```
本地文件 / 网络 URL ─ffmpeg─► H.264/H.265 裸流 ─mpegts 封装─► stdout
   │  scale=W:H + pad + fps（强制恒帧率）
   │  x264 / x265: aud=1（每帧带访问单元分隔符）、keyint=1×fps、bframes=0、repeat-headers=1
   │  bsf dump_extra：每个关键帧前重复 SPS/PPS，保证中途接入的客户端也能解码
   ▼
TsDemuxer（media/pipeline.py）
   · 188 字节定长包，按 PID 过滤，只认 PES 起始且 stream_id=0xE0~0xEF 的视频 PID
   · 每个 PES = 一帧（Access Unit），从 PES 头解析 33bit PTS
   · Annex-B 切分 → 丢掉 AUD → 输出 NAL 列表
   ▼
StreamSource._run
   · 时间戳：rt_clock += (pts - prev_pts)，异常跳变（文件循环、seek）时用 1/fps 补齐 → 单调递增
   · 节奏：target = t0 + rt_clock/90000，sleep 到点再发（落后 >1.5s 自动重新对齐）
   · 参数集（SPS/PPS/VPS）缓存，供 DESCRIBE 生成 SDP
   ▼
每个客户端通道 RtspChannel
   · 新接入（PLAY）先标记 need_keyframe，跳过 GOP 中间的帧，从下一个 I 帧开始发 → 客户端不会缺参考帧
   · packetize(NAL, codec, mtu=1400)：H.264 → FU-A（类型 28），H.265 → FU（类型 49）
   · 依次发 RTP，序号自增，一帧的最后一个包置 Marker 位
   · UDP：sendto 客户端协商端口；TCP：交织帧 `$ + channel + len + payload`，独立写线程 + 有界队列（读不过来就丢帧，不阻塞其他客户端）
```

### RTP 打包示意（H.264，一帧 = 1 个 IDR 被切成多片）

```
NAL: [67 SPS][68 PPS][65 IDR slice (≈40KB)]
  ├─ SPS/PPS  < MTU  → 单 NAL 单元包（原样）
  └─ IDR 切片 > MTU  → FU-A
       包1: [F|NRI|28][S=1,E=0,type=5][前 1398 字节]
       包2: [F|NRI|28][S=0,E=0,type=5][中 1398 字节]
       包3: [F|NRI|28][S=0,E=1,type=5][剩余字节]  ← Marker=1
```

### 2.1 输入源：本地文件与网络流

`stream.source` 一个字段同时承载本地路径和 URL，靠 `app/models.py` 的 `is_network_source()`
（正则 `^(http|https|rtsp|rtsps|rtmp|rtmps|udp|rtp|srt|tcp)://`）分流，`build_ffmpeg_cmd` 据此加不同输入参数：

| 源类型 | 输入侧额外参数 | 说明 |
| --- | --- | --- |
| 本地文件 + `loop=True` | `-stream_loop -1` | 原地循环，模拟「永不结束的摄像机」；PTS 由 ffmpeg 连续递增 |
| 本地文件 + `loop=False` | 无 | 放到文件尾 ffmpeg 正常退出（rc=0），由上层收尾 |
| RTSP / RTSPS | `-rtsp_transport tcp\|udp` | 由设置项 `rtsp_input_transport` 决定，默认 tcp（抗丢包） |
| HTTP / HTTPS / RTMP(S) | `-reconnect 1 -reconnect_streamed 1 -reconnect_delay_max 5` | 源端断流时 ffmpeg 自己先就地重连一次 |
| 任意 | `-rw_timeout 20000000`、`-fflags +genpts` | 20s 读写超时，避免半死连接把进程挂住；网络源无时间戳时补生成 PTS |

输出侧参数与源无关：恒帧率（`fps=` 滤镜）、`keyint=fps`（GOP 1 秒）、`bframes=0`、
`aud=1`、`repeat-headers=1` + `bsf dump_extra`。

### 2.2 网络源的容错：两层重连

```
StreamSource._run（外壳，只负责重连策略）
   while not _stopping:
        rc = _run_once()            ← 真正的 ffmpeg 进程 + 解复用 + 分发
        网络源且非主动停止 → 退避 3s→6s→…→30s 上限，日志「第 N 次重连」
        本地文件 → 直接退出（文件坏了重连也没意义）
```

这样网络源有两道保险：ffmpeg 参数层面先就地重连（快），
进程真的退出后再由外层按退避重启（慢但兜底）。
重连期间 `state` 回到 `starting`，参数集缓存不清空，
所以已连上的客户端不会因为源抖动而 DESCRIBE 失败（`_m_describe` 对网络源放宽到 5 秒等参数集）。

另外客户端侧不受影响：重连是换了一个新的 ffmpeg 进程，
`StreamSource` 对象和 `RtspChannel` 列表不变，RTP 序号继续递增，客户端只会看到画面短暂停顿。

### 2.3 播完之后：循环还是停止

`StreamSpec.loop` 控制的是**播放结束之后**的行为，与「连接出错」是两条独立路径：

```
_run_once 正常收尾判定
   rc == 0 且本轮出过帧  →  _last_clean_eof = True   （真·播放结束）
   其他                  →  state = error + 错误日志   （真·出错）
          │
          ├─ loop=True  →  记「第 N 次循环重播」，0.2s 后重开一遍（同源、同 URL）
          └─ loop=False →  state = stopped，进程结束，日志「播放结束，已停止」
```

- 本地文件 + `loop=True`：循环交给 ffmpeg 的 `-stream_loop`（更省，无进程重启），`_run` 基本不会被触发；
- 网络源 + `loop=True`：直播源永远播不完，只有点播源（mp4、有限 m3u8）会走到「重开地址」这一步；
- 出错（rc≠0 或本轮一帧都没出）在本地文件上直接结束，网络源仍按 2.2 的退避重连，**不受 loop 开关影响**；
- 播完停止后路径不摘除，但 `DESCRIBE` / `SETUP` 会先查 `stream.state`：只要不是 `starting`/`running`
  就立刻回 `503 Service Unavailable` + `Retry-After: 1`，避免拿缓存里的旧 SPS/PPS 骗客户端连进来却收不到帧。

循环重播时最怕时间戳回退：新起的 ffmpeg 进程 PTS 从 0 重新计数，如果直接拿来当 RTP 时间戳，
已经连着的客户端会看到时间戳倒流、reference 帧错乱。所以 `StreamSource` 用 `_clock_base` 跨轮累计：

```
本轮 rt_clock = self._clock_base        # 从上一轮结束处接着走
每帧     rt_clock += (pts - prev_pts)
收尾     self._clock_base = rt_clock + frame_delta   # 给下一轮留一帧间隔
首帧对齐 t_start = now - rt_clock / 90000            # 换算成能贴合当前时刻的绝对时间轴
```

这样循环接缝处 RTP 时间戳单调递增，客户端只会看到一帧的正常间隔；
自检里的「循环切换处解码无告警」就是跑过一次真实的循环边界来守这条性质。

### 2.4 哔哩哔哩视频页：为什么不能直接喂给 ffmpeg

```
视频页 URL（带 spm_id_from 之类的追踪参数）
    │  parse_video_id：取 BV / av 号与 ?p=N（b23.tv 短链先跟 302 展开）
    ▼
GET x/web-interface/view?bvid=..    → cid、标题、时长、分 P 列表
    ▼
GET x/player/playurl
    cid=..&qn=120&fnval=4048&fourk=1&try_look=1  (+ Cookie: SESSDATA)
    ▼  data.dash.video[]：同一分辨率常给 avc1 / hev1 / av01 三份编码
选轨：优先 avc1 → 分辨率最高 → 码率最高，且不超过 1080P
    ▼
ffmpeg -user_agent UA -headers "Referer: https://www.bilibili.com/\r\n" -i <直链>
```

四条实测结论（都是踩出来的，别回退）：

1. **必须带 Referer**：B 站 CDN 对缺少 Referer 的请求直接 403；`-user_agent` 同理要带上。
   这两个参数通过 `build_ffmpeg_cmd(..., input_args=...)` 插到 `-i` 之前。
2. **必须带 `try_look=1`**：不带它时匿名最高只有 480P（dash 里最大 852×480）；
   带它以后同一视频能拿到 `1920×1080 / avc1.640032`。`qn=120` 只是「尽量要」，实际档位由服务端按登录态给。
3. **不要加 `platform=html5`**：加了接口会只回 `durl`（单片 mp4、通常 480P）而不回 DASH，选轨逻辑直接落空。
4. **直链带签名、有时效**：所以不是解析一次缓存到底，而是 `StreamSource._run_once` 每次启动都重解析一遍
   （循环重播、断线重连各算一次），长期挂着也不会因为签名过期突然断流。

Cookie 会拼进 ffmpeg 命令行，所以日志里用 `bilibili.mask_secret()` 把 SESSDATA 值替换成 `******`。

为什么不取 4K：输出本来就要按用户设定的分辨率重编码，源超过 1080P 只是白花解码 CPU，收益不大；
需要的话改 `bilibili.resolve(..., max_height=2160)` 即可。

### 2.5 主码流 / 子码流：一条流两个编码器

真实摄像机对外只是「一个通道」，内部却有两套编码与两条 RTP 流：主码流吃大带宽，子码流供低带宽客户端。
本程序以前是「一路流一个编码器，所有路径共用参数」，`102` 拿到的和 `101` 一模一样。
现在把这条路补上：**同一个 `StreamSpec` 可以派生出两个 `StreamSource`**。

```
StreamSpec（name=车间门口, 1920×1080@25 / 4096kbps, sub:704×576@25 / 512kbps）
   │ split_routes()：按 Route.sub 拆成主/子两组路径
   ├── 主：/Streaming/Channels/101, /cam/realmonitor?...subtype=0
   │      → replace(spec, routes=主) → StreamSource #1 → server.add_route(...)
   └── 子：/Streaming/Channels/102
          → replace(spec, name+="·子码流", 宽高/fps/kbps=sub_*, id=f"{id}-sub", routes=子)
          → StreamSource #2 → server.add_route(...)
```

关键设计点：

1. **按路径分档，而不是按参数猜**：`Route.sub` 是显式标记（界面勾选子流路径时写入），
   旧配置没有这个字段时由 `is_sub_route()` 按厂商的 `sub_path` 兜底推断（海康 `102`、大华 `subtype=1`、
   宇视/索尼 `video2`、晶睿 `live2.sdp`……），所以老 `config.json` 不用迁移就能正确分档。
2. **两个编码器共用同一个源**：各自起 ffmpeg 从同一个 `source` 读（本地文件各自从头读；网络源各自拉流）。
   不用「一次解码两路编码」，因为 ffmpeg 单片 tee 到两个编码器会让节奏互相牵制，
   而现在两个进程各自有独立时钟、独立重连、独立循环，互不拖累——更像真机的两路独立码流。
3. **路由各自绑自己的源**：`RtspServer.add_route(stream, path, vendor)` 里 stream 就是编码器对象，
   所以 `102` 的 SDP 参数集、RTP 时间戳、SSRC、客户端计数全部来自子编码器，
   与 `101` 完全隔离；同一个客户端同时接 `101` 和 `102` 会拿到两条独立会话。
4. **运行态按 spec.id 聚合**：`engine.sources[id]` 与 `engine.sub_sources[id]` 分开存，
   对上层仍然只暴露「一条流」：`stats()` 把主/子状态合并（running > starting > error > stopped），
   客户端数与帧数求和，并额外给出 `main_state` / `sub_state` / `sub_clients` 供界面分列显示。
5. **优雅退化**：
   - 只勾了子流路径、但没启用子码流 → 全部路径合并到主编码器（不会出现「一条流都没有」）；
   - 只勾了主流路径 → 勾不勾子码流开关都只起一个编码器（不白花 CPU）；
   - 启用子码流但没有任何子路径 → 同上，`use_sub = sub_enabled and bool(sub_routes)`。
6. **启停按整条流**：`stop_stream(spec.id)`、`update_stream()`、`stop_all()` 都是主+子一起处理，
   编辑保存后若原流在运行，会先停掉两个编码器再一起重启，避免只换掉主码流留下旧子流。
7. **界面层「选厂商 = 选画质」**：`StreamDialog._on_tree_changed` 发现用户勾上某条子流路径时，
   调用 `VendorPreset.default_size("sub")` 把子码流参数填成该厂商的辅流出厂值（海康 `704×576@512`、
   大华 `640×480@512`）并自动打开「启用」开关；用户手动改过分辨率/帧率/码率后，
   界面不再声称「按厂商默认」（`_sub_autofill` 会被清空）。
   这一层只在 UI 做，`StreamSpec` 里存下来的是具体数值，引擎不知道也不关心「厂商默认」这件事。

代价与注意：

- 这一路会多一个 ffmpeg 进程；`704×576@512kbps`（D1）大约只有 1080P 主流的 1/10 编码开销，
  `1280×720@1024kbps` 约 1/3。
- 网络源会变成「同一地址拉两次」，B 站直链因此会解析两次（每次 `_run_once` 都重新解析，签名互不影响）。
- 子码流的 GOP 仍按自己的 fps 算（`keyint = round(fps)`），所以 15fps 的子流是 15 帧一个关键帧，
  与主码流不要求对齐——真机也不对齐。

## 3. RTSP 交互时序

```
客户端                                  服务端
  │ OPTIONS  rtsp://ip:8554/Streaming/Channels/101
  │ ─────────────────────────────────────►│ 200  Public: OPTIONS,DESCRIBE,SETUP,PLAY,...
  │                                       │      Server: Hikvision
  │ DESCRIBE （同上 URI）
  │ ─────────────────────────────────────►│ 等待参数集就绪（最多 3s）
  │                                       │ 200  Content-Type: application/sdp
  │                                       │      Content-Base: rtsp://ip:8554/Streaming/Channels/101
  │                                       │      body = SDP（m=video 0 RTP/AVP 96,
  │                                       │              a=rtpmap:96 H264/90000,
  │                                       │              a=fmtp:96 packetization-mode=1;profile-level-id=..;sprop-parameter-sets=..,
  │                                       │              a=control:trackID=1）
  │ SETUP  .../Streaming/Channels/101/trackID=1
  │        Transport: RTP/AVP/UDP;unicast;client_port=5000-5001
  │ ─────────────────────────────────────►│ 200  Transport: RTP/AVP/UDP;unicast;client_port=..
  │                                       │      server_port=6000-6001;ssrc=1A2B3C4D
  │                                       │      Session: 8FE1C2A0;timeout=60
  │ PLAY
  │ ─────────────────────────────────────►│ 通道 active=True，开始推送 RTP
  │                                       │ 200  RTP-Info: url=...;seq=312;rtptime=90
  │ ◄──────────── RTP 流 ─────────────────│ （每 5s 一条 RTCP SR）
  │ GET_PARAMETER（保活）                  │ 200
  │ TEARDOWN                              │ 200，通道关闭
```

**路径解析的容错**（真实客户端行为差异很大）：

1. 客户端把 `a=control` 拼到 URL 后面 → `rtsp://ip/cam/realmonitor?channel=1&subtype=0/trackID=0`，
   服务端先用正则剥掉尾部的 `/trackID=*` 再解析；
2. 查询串顺序不同（`subtype=0&channel=1`）→ 路由键用「查询参数排序后」的归一化字符串；
3. 客户端漏掉查询串 → 退化为按 path 匹配。

这三点是为**大华主/辅码流**准备的：`subtype=0` 与 `subtype=1` 必须区分成两路不同画质的流。

## 4. 厂商模拟的落点

| 模拟项 | 实现位置 |
| --- | --- |
| 路径（含查询串） | `app/vendors.py` 的 `main_path` / `sub_path`，可被界面自定义路径覆盖 |
| SDP 媒体级 `a=control` | `vendors.py` 的 `control`（`trackID=1` / `trackID=0` / `track1` / `streamid=0`） |
| `Server` 响应头 | `vendors.py` 的 `server_header`，OPTIONS/DESCRIBE/SETUP/PLAY 都会带上 |
| 主/辅码流默认画质 | `main_size` / `sub_size`（分辨率、帧率、码率），选中厂商+码流类型时自动填入 |
| 参数集声明 | `sdp.py`：H.264 用 `sprop-parameter-sets` + `profile-level-id`（从 SPS 的 1~3 字节直接取），H.265 用 `sprop-vps/sps/pps` |
| 恒定帧率 | ffmpeg `fps` 滤镜 + 服务端按 PTS 匀速推送 |

## 5. 关键取舍

- **不用 MediaMTX**：现成服务器按 URL path 匹配会丢查询串，无法区分大华主辅流，Server 头/SDP 也不可定制。
- **不直接用 ffmpeg 的 RTP 输出**：那只能单客户端、时间戳与节奏不可控、无法按厂商定制 SDP。
- **编码与分发解耦**：一路流只编码一次，N 个客户端共享，成本与客户端数无关。
- **TCP 通道独立写线程 + 有界队列**：慢客户端只会丢自己的帧，不会拖住其他客户端或编码线程。
- **循环优先交给 ffmpeg（`-stream_loop`），而不是自己重复喂文件**：本地文件循环零进程重启、PTS 天然连续；
  只有「关掉循环后重新启动」或网络点播源才会重开进程，这时用 `_clock_base` 把时间戳接上。
- **哔哩哔哩不引入 yt-dlp**：只用官方 web 接口 + 标准库（urllib/json/hashlib），不额外加依赖；
  代价是番剧、付费课、互动视频不支持，这类链接会返回明确原因而不是卡住。
- **帧数据零拷贝到客户端**：payload 列表复用，只在每个通道加 12 字节 RTP 头。
- **主子码流用两个编码器而不是一个解码+两个编码**：两路严格等价于两台独立摄像机通道——独立时钟、独立重连、
  独立循环；一个进程里 tee 两路编码反而会让节奏互相牵制，且任一路抖动都会拖累另一路。

```
PASS  播完停止后客户端被明确拒绝  [503 Service Unavailable]

PASS  循环切换处解码无告警
PASS  主子码流双编码器均已就绪      [main=running sub=running]
PASS  主码流路径分辨率正确          [1920×1080]
PASS  子码流路径分辨率正确          [704×576]

PASS  子码流连续解码 3 秒无告警
PASS  聚合状态含主/子两路            [state=running main=running sub=running]
PASS  停止后路由已摘除（返回错误）
PASS  服务正常关闭
```

网络源四项的做法：自检在 `127.0.0.1:8099` 起一个临时 HTTP 服务（`ThreadingTCPServer`，静默日志），
直接饲料 `samples/demo_720p.mp4`；HLS 分支先用 ffmpeg `-c copy -f hls -hls_time 2 -hls_list_size 0`
把样例切片到 `samples/hls/index.m3u8`，再以 `http://127.0.0.1:8099/hls/index.m3u8` 作为源。

循环四项用一段 2 秒短片段（`samples/short_2s.mp4`，首次自检自动生成）：
`loop=False` 应该播完变 `stopped`，此时客户端再连应被 503 明确拒绝；
`loop=True` 出帧数要超过 70 帧（2 秒≈50 帧，>70 说明进入第二遍）；
再用真实客户端解 4 秒，从中间跨过一次循环接缝，确认没有解码告警（时间戳回退会在这里立刻暴露）。

主子码流六项：同一路流挂 `101`（主）与 `102`（子，`Route(sub=True)`）、`sub_enabled=True` 且
子参数 704×576@25fps/512kbps（出厂默认辅流档，与主码流 1080P@4096 拉开分辨率差），先等两个编码器都 `running`，然后用 ffprobe 分别量 `101` 与 `102` 的分辨率
（必须一个 1920×1080、一个 1280×720），再用 ffmpeg 各解 3 秒确认两路都无解码告警，
最后核对 `engine.stats()` 聚合出的 `main_state`/`sub_state` 都是 `running`。

哔哩哔哩解析要联网，`selftest.py` 是离线自检，所以单独放了 `tools/bili_check.py`：

```
解析中…（匿名默认带 try_look，普通视频可拿到 1080P）
标题    ：在非洲街头被混混围攻…
分辨率  ：1920×1080（1080P，id=80）
编码    ：avc1.640032
ffprobe 直链结果：codec_name=h264  width=1920  height=1080  avg_frame_rate=30/1
```

端到端也验过一次：起服务 → 挂哔哩哔哩源 → ffprobe 转出的 RTSP 得到 `h264 1920×1080@25` → 连续解码 6 秒零告警。

其中「连续解码无告警」这几项最值钱，抓到的都是真 bug / 真坑：

1. **H.264 FU-A 类型字段取错**：H.264 的 NAL 头只有 1 字节，如果误取第 2 字节当类型，大 IDR 帧会被重组错类型，
   ffmpeg 侧报 `sps_id out of range`；
2. **客户端从 GOP 中间接入**：H.265 的多参考帧会报 `Could not find ref with POC ...`，
   所以新接入的会话必须先等一个关键帧；
3. **moov 在尾部的 mp4 + 不支持 Range 的 HTTP 服务器**：ffmpeg 为了读尾部 moov 会发起带 Range 的请求，
   Python 的 `SimpleHTTPRequestHandler` 不支持 Range、忽略请求头从头整段回送，ffmpeg 把文件头当成 moov 解析，
   报 `Invalid NAL unit size` / `Cannot determine format of input stream`。
   规避方式：源文件加 `-movflags +faststart`（`tools/make_sample.py` 就是这么生成的），或换成支持 Range 的服务器。
   这个坑只在本地简易 HTTP 源上出现，Nginx/OSS/CDN 都有 Range 支持。

## 8. 主题与视觉规范（Aurora Glass 现代毛玻璃，深色 / 浅色双主题）

### 8.1 结构与设计意图

视觉层分三个文件：

| 文件 | 职责 |
| --- | --- |
| `app/ui/theme.py` | 尺寸 token、双套色板、共享 QSS 模板、运行时小图标；`prepare_qss(theme)` 是唯一出口 |

三条设计约束（也是这一版相对旧版的关键改动）：

1. **玻璃必须有色彩来源。** 半透明白 alpha 叠在灰黑底上只会得到一块脏灰色板子。新版背景画布铺

3. **信息分层靠结构，不靠颜色。** 命令按用途分成三组胶囊；表格只放规格概览，长内容（完整地址）
   进详情栏逐条展示；日志收成可折叠窄条。

- **尺寸 token（两套主题完全一致，只换色值）**

### 8.3 玻璃实现（AuroraCanvas + GlassCard）

**红线**：不使用 `WA_TranslucentBackground` / 整窗真透明接桌面——那样 `window.grab()` 会拍成黑底，
截图与真实观感不一致。玻璃全部在窗口内部自绘，保证 grab 出来的图就是用户看到的样子。

`AuroraCanvas`（窗口最底层背景）：

1. 竖向线性渐变（深色 `#080B12` → `#04060A`，浅色 `#E8EDF7` → `#F7F9FD`）；
2. 三个大径向光晕，0 / 0.42 / 1 三个色标由实到透：左上紫罗兰 @0.26、右下青绿 @0.17、
   左下玫红 @0.11（浅色主题同样三团，alpha 降到 0.10~0.16）；光晕越强，卡片里的文字越容易串色，
   所以深色主题保持「看得见颜色、压得住文字」的强度；
3. 暗角：以内容区中心为圆心的反向径向渐变，四角压暗（仅深色主题，alpha 0.58）；
4. 一层 ≤3% 的细半点阵噪点（固定随机种子，消掉渐变的色带）。

整幅背景缓存为一张 QPixmap，仅在 `resizeEvent` 或 `set_theme` 时重算。

`GlassCard`（每张卡片）：

1. 从画布缓存中按自身几何（外扩模糊半径 padding）截取背景切片；
2. 离屏高斯模糊：`QGraphicsBlurEffect` 半径 **22px**，经 `QGraphicsScene` 渲染到一张缓存 QPixmap；
3. 叠**带色调的玻璃霜面**（竖向渐变，顶部略实、底部略透）：
   深色 `#0C1220` @70%（强玻璃 @80%），浅色白 @70%（强玻璃 @86%）；
4. 1px 玻璃边：深色 白 @13% / 强边 @22%，浅色 `#0B1220` @5.5% / 强边 @11%；
5. 顶部 1px 高光：横向渐变，中间最亮、两端渐隐，模拟顶光打在玻璃边缘；
6. 柔和投影：`QGraphicsDropShadowEffect`，模糊 30、偏移 0/+8，深色黑 @42%、浅色冷灰 `#1B2A4A`@13%。

**缓存策略与性能**

- 模糊切片按卡片缓存（`self._blur`），只在卡片 `resizeEvent`、换主题、或画布失效
  （`invalidate_blur()`）时重算；`paintEvent` 只做 `drawPixmap` 与分层填充，不做实时模糊。
- 画布背景同样缓存为一张 Pixmap，拖动窗口 / 缩放尺寸时才重建；日常重绘（hover、选中、日志追加）
  不触发模糊或画布重建。
- 切换主题：画布 `set_theme` 重建一次缓存 → 各卡片 `invalidate_blur()` 清切片缓存 → 重绘；
  单窗口五张卡片，离屏模糊在尺寸稳定后只发生一次，无逐帧开销。

### 8.4 主题切换链路（不打断运行中的流）

```
顶栏分段按钮 / 设置对话框下拉
        │
        ▼
MainWindow.apply_theme(theme, save=True)
  · config.theme = theme
  · 刷新本进程内的状态色 / 日志色字典
  · canvas.set_theme → 各卡片 set_theme + invalidate_blur
    → 标题栏按钮 / 分隔线 / 品牌标记 / 状态胶囊 / 地址行 set_theme
  · QApplication.setStyleSheet(prepare_qss(theme))
  · 同步分段按钮选中态 + Windows 标题栏深浅色
  · config.save() 落盘（冒烟测试可传 save=False）
```

切换路径**不调用 Engine 的任何启停方法**：不重启编码器、不断开 RTSP 客户端、不清空日志、
不重建 Engine / MainWindow。已挂客户端的会话、编码器子进程 PID 在切主题前后保持不变（冒烟脚本实测）。

主题持久化在 `AppConfig.theme`（`dark` / `light`）：旧配置缺字段默认 `dark`，非法值回退 `dark`；
`to_dict / from_dict` 兼容未知字段缺失。配置路径解析：源码运行用项目根 `config.json`；
PyInstaller 冻结时优先 exe 同目录 `config.json`，目录不可写再退回 `%APPDATA%\RtspCamSim\config.json`。

### 8.6 WCAG 对比度核算（相对亮度公式，比值 = (L1+0.05)/(L2+0.05)）

正文 / 次要 / 表头 / 按钮文字要求 ≥ 4.5:1；600 字重状态胶囊 ≥ 3:1。
前景色先按玻璃参数与画布底色 `blend` 合成实色，再按相对亮度公式计算。

| 配对 | 深色 Obsidian | 浅色 Frost |
| --- | --- | --- |
